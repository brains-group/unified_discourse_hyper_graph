# MEQA: dataset analysis and knowledge-graph evaluation protocol

**Paper:** Li, Wang, Tran, Xia, Du. *MEQA: A Benchmark for Multi-hop Event-centric Question Answering with Explanations.* NeurIPS 2024, Datasets & Benchmarks track (UT Dallas).
**Repo:** https://github.com/du-nlp-lab/MEQA (cloned at `unh_v1/MEQA`, HEAD `66fe3bf`).
**Report date:** 2026-09-25.

Every claim below is tagged with where it comes from:
- **[paper]**: stated in the paper (section or table given).
- **[verified]**: I measured it on the released JSON files, the repo code, or the original WikiEvents files.
- **[inferred]**: my reading of the code or data. It is well supported but not stated anywhere by the authors.

## 1. Short answer to your question

**MEQA is a single-document reading-comprehension task, the same kind of setup as our insurance-contracts dataset. It is not HotpotQA-style passage pooling.**

- A question's `context` is **one complete news article**. It is not a bundle of gold evidence and it is not a list of passages. **[verified]** All 211 source documents match a full document from the WikiEvents dataset exactly (after whitespace normalization). None are truncated and none are concatenations.
- Many questions share one article: a median of 13 questions per article in the test split. **[verified]** Each question is answered from its own article only. The authors built every question by picking events **inside that one document**. **[paper §4.1, verified in `src/generator/sample.py`]**
- The task never requires reasoning across documents. There is no retrieval step and there are no distractor documents. The paper's input format is `C + Q → A`, where C is the whole document. **[paper §6.2, verified in `src/llm/llm_inference.py`]**
- "Multi-hop" in MEQA means hopping **within one article**, over events and entities (entity → event → related event → argument). It does not mean hopping across passages.

So of the options you listed, MEQA is **"take one document at a time, with a set of questions for that document."**

**Can it be used for KG evaluation?** Yes. The faithful way is to **build one KG per document and answer that document's questions from its own KG**, exactly as in the insurance-contract setup. The test split is small (22 documents, about 13k tokens in total), so graph construction is cheap. The main caveat, covered in §7: documents average about 785 tokens, so a plain "put the whole article in the prompt" baseline is strong. A KG method has to earn its keep through structure, not retrieval.

## 2. What the paper says

### 2.1 Motivation
Existing multi-hop QA benchmarks (HotpotQA, 2Wiki, MuSiQue) hop over **entity–entity** relations. MEQA targets **event-centric** reasoning **[paper §1, App. A]**:
- **event–argument** relations (for example, "major general" is the VICTIM of *kills*);
- **event–event** relations, temporal (BEFORE/AFTER/CONTAINS) and causal (CAUSES/CAUSED BY).

The paper stresses that two arguments of the same event have no direct relation, so a reasoning chain has to go through the event trigger. The chain alternates between entities and events, for example: Al-Monitor →(communicator) *reported* →(after) *kills* →(victim) major general.

### 2.2 Source data
- The source is **WikiEvents** (Li et al., 2021): news articles annotated with KAIROS event types, event triggers and argument roles. It has 246 documents and 33 event types. **[paper App. C; verified: 206 + 20 + 20 = 246 docs]**
- MEQA uses **211** of those documents. **[paper §5; verified]**
- WikiEvents has **no** event–event relation annotations (0 relation mentions across all 246 docs). **[verified]** The temporal and causal relations in MEQA were **generated by an LLM** (GPT-3.5) and then curated by annotators. **[paper §4.1, App. G]**

### 2.3 Question types (five "strategies") [paper Table 1, §3.1]
| Strategy | Share | What it tests | Example |
|---|---|---|---|
| S1 Event Relation | 49.7% | find a start event → find the event related to it by time or cause → extract an argument | "Who died before Al-Monitor reported it online?" |
| S2 Entity Bridging | 37.1% | chain of events connected by shared entities (up to 4 hops) | "Which transportation method did Whitelaw use to reach the place where 11 people died?" → Plane |
| S3 Listing / Counting | 6.2% | find all matching events, then count | "How many victims are mentioned in the whole text?" → 5 |
| S4 Comparison | 5.0% | count per group, then compare | "Which one, IED or IS, killed more victims?" → IS |
| S5 Unanswerable | 2.0% | the chain breaks, so there is no answer | "Who traveled to the place where 21 bombs were manufactured?" |

### 2.4 Construction pipeline [paper §4]
1. **Compose chains from gold event structures in one document.** For S1, pick a random pair of events and have an LLM label their relation. For S2, pick a start event and add events that share an argument, up to 4 hops. For S3–S5, annotators pick the events by hand.
2. **Remove shortcuts.** Drop a chain if an intermediate or end event can be located uniquely by its trigger plus the kept roles, because then the earlier hops are unnecessary.
3. **Merge chains** that share the same start event and relation, and combine their answers. This is why many answers are lists.
4. **Generate template questions** from KAIROS templates by replacing the answer with a wh-word. Each sub-question becomes one explanation step.
5. **Human curation.** Five student annotators paraphrased the questions and explanations and marked all answer spans. They were paid about $0.65 per question.

### 2.5 Statistics [paper Table 7]
| | Train | Dev | Test | Overall |
|---|---|---|---|---|
| Documents | 189 | 20 | 22 | **211** |
| Questions | 1,674 | 282 | 287 | 2,243 |
| Avg. document length (words) | 695.4 | 815.2 | 494.9 | 676.4 |
| Avg. hops | 2.6 | 2.6 | 2.6 | 2.6 |

Note that 189 + 20 + 22 = 231, not 211. The paper's own table therefore implies that the dev documents overlap with the train documents. I confirmed this in the data (§3.3).

### 2.6 Evaluation in the paper [paper §6]
- **Answers:** precision, recall and F1 from the HotpotQA script. The paper argues that **recall** is the more informative number for LLMs.
- **Explanations:** *completeness* (a step-wise, order-preserving match of predicted QA steps against gold steps, using LLM semantic matching; App. H) and *logical consistency* (an LLM judges each step against the previous steps).
- **Setting:** the full document goes in the prompt. Few-shot GPT-3.5-turbo-1106, with Claude-3-Haiku, Llama-3-70B and GPT-4 in the appendix. A T5 model is also fine-tuned.
- **Headline results on test, GPT-3.5 [paper Tables 2 and 4]:**

| Method | P | R | F1 |
|---|---|---|---|
| Few-shot (C+Q→A) | 0.190 | 0.536 | 0.238 |
| CoT-QA (C+Q→E+A) | 0.283 | 0.390 | 0.294 |
| CoT-QA + "Full Event KG" | 0.530 | 0.530 | 0.494 |
| Few-shot + "Full Event KG" | 0.454 | 0.636 | 0.458 |
| Human (100 test questions) | 0.783 | 0.836 | 0.811 |

The paper reads these results as showing that adding structured event information helps a lot. See §5.3 for an important caveat about what "Full Event KG" actually contains.

## 3. What is actually in the released data [verified]

### 3.1 Files and schema
`data/collected_{train,dev,test}.json` are JSON lists of records like this:
```json
{"example_id": "train_148_s1_1",
 "context": "<full WikiEvents article text>",
 "question": "Where were the bombs planted before the explosion of twenty bombs?",
 "answer": "around Belfast",
 "explanation": ["What event contains twenty as the explosive device? exploded@162",
                 "What event is before #1 and has a place? planted@151",
                 "Where were the bombs planted in #2? around Belfast"]}
```
`sample.json` (187 records) is an older, differently formatted sample. It is not needed.

### 3.2 Counts: released vs. paper
| | Train | Dev | Test | Total |
|---|---|---|---|---|
| Released records | 1,629 | 182 | 288 | **2,099** |
| Paper, Table 7 | 1,674 | 282 | 287 | 2,243 |
| Repo README | | | | 2,093 |

The three sources disagree. The released files are the ground truth for anything we run.

### 3.3 How `context` maps to documents
- **`example_id` = `{WikiEvents split}_{WikiEvents line index}_s{strategy}_{k}`.** The prefix is the **source WikiEvents split, not the MEQA split**. For example, MEQA test contains `train_148_*`, because WikiEvents train document 148 was assigned to the MEQA test split. `s35` is a single bucket that covers strategies 3, 4 and 5.
- **Every `context` is exactly the `text` of the WikiEvents document named by that prefix.** This holds for all 211 distinct document ids after whitespace normalization. The released data does not truncate, excerpt or concatenate anything.
- There are **209 unique texts**. WikiEvents itself contains duplicate articles under different ids: `train_115`/`train_176` and `train_149`/`train_188` have identical text.
- Some document ids have slightly different whitespace in different MEQA splits (for example, "Saturday.The" vs. "Saturday. The"). **Deduplicate on whitespace-normalized text, not on the raw string.**

| | Unique docs | Questions per doc (min / median / max) | Words per doc (avg) | Tokens (cl100k) |
|---|---|---|---|---|
| Train | 188 | 1 / 8 / 25 | 610 | 151,446 |
| Dev | 20 | 1 / 7 / 25 | 711 | 18,665 |
| Test | 22 | 5 / 13 / 26 | 446 | 12,943 |
| All (deduplicated) | 209 | | | 164,135 |

The longest document has 4,067 words (a drone-policy article). The shortest has 13 words (just a headline).

### 3.4 Split contamination
- **Dev reuses train documents.** All 20 dev documents also appear in train. All 182 dev `example_id`s also appear in train. Most dev questions are **paraphrases of the train question with the same id**, and 18 are identical. Example:
  - train `train_31_s2_0`: "Where did the explosions take place?" → birmingham
  - dev `train_31_s2_0`: "Where were the explosions?" → birmingham

  Dev is therefore not a held-out split.
- **Test is disjoint from train by document id, with one exception.** Test document `train_176` has the same text as train/dev document `train_115`, because of the WikiEvents duplicate. None of the 288 test (context, question) pairs appear in train, and only 2 test question strings appear in train.

### 3.5 Keys and duplicates
- **`example_id` is not unique.** There are 106 duplicate ids in train, 12 in dev and 19 in test, and in each case the records hold *different* questions. Use `(split, index in file)` or a hash of `(context, question)` as the key.
- Exact duplicate (context, question) pairs: 26 in train, 4 in dev, 7 in test.

### 3.6 Answers
- `answer` is usually a string. Multiple answers are **comma-separated**, for example "major general,local commander,lieutenant general". In test, 252 questions have one gold item, 18 have 2, 8 have 3 and 3 have 4 or more.
- **Unanswerable questions** are stored inconsistently: as `[]` (39 train / 2 dev / 6 test) or as `""` (7 / 1 / 1). One test record (`train_194_s35_1`) has an **empty question string**.
- **Answers are mostly, but not always, spans.** The share of gold items that appear verbatim (case-insensitive) in the context is 85.3% in train, 81.7% in dev and 77.6% in test. The rest are paraphrases, numbers or whole sentences. In test, 39 non-list answers are longer than 6 words, for example "Tamerlan detonated at Boston and killed by police" or "bomb was manufactured by bought chemicals".
- Some gold answers are noisy: "people,people,people", "it", "Raham", a truncated "Rahami".

### 3.7 Questions
- **Test questions are noticeably less polished than the paper's examples.** 95 of 288 test questions contain two or more wh-words, a rough proxy for leftover template text. Examples: "who detonated or exploded by using what explosive device?", "detonated or exploded at where place because died killed by brothers killer". Some questions ask for two things at once ("who bought what online and bought by whom"), and the gold answer is then a sentence.
- **Counting questions count WikiEvents annotations.** For example, "How many events are related to death?" → 2, where the explanation shows `deaths@70, died@177`. The answer is the number of **annotated trigger mentions** in the document, not the number of real-world events. No independently built KG can be expected to reproduce these counts exactly. There are 7 such questions in test and 17 "how many" questions in total.
- Questions are phrased relative to the document. Only 1 test question contains a word like "document", "article" or "mentioned". Most refer to entities or events that are only unambiguous inside their own article, such as "Where were the explosions?" or "Who killed the person who died?".

### 3.8 Explanations and recoverable gold evidence
- S1 explanations always have 3 steps. S2 has 2–4 steps. S3–S5 have 0–3 (unanswerable questions have none).
- **`word@N` in an explanation is the WikiEvents token index of an event trigger.** This matched a WikiEvents trigger start in 1,548 of 1,553 anchors. Each WikiEvents trigger has a `sent_idx`, so **the gold evidence sentences can be recovered** for anchored questions. That makes a retrieval or evidence-recall metric possible.
- Coverage is partial. In test, anchors exist for S1 88/147, S2 2/127 and S3–S5 8/14. That is 98 of 288 questions, and almost no entity-bridging (S2) questions.

### 3.9 Topical overlap between documents
Many documents cover the same real-world events. Among the 209 unique documents, "Boston Marathon" appears in 36 and "Tsarnaev" in 31. Among the 22 test documents, "Boston Marathon" appears in 5 and "Tsarnaev" in 4. This matters only if you pool documents into one corpus (§6.2).

## 4. Comparison with the other dataset philosophies

| | HotpotQA / MuSiQue (as we use them) | Insurance contracts (ours) | **MEQA** |
|---|---|---|---|
| Unit given with a question | gold + distractor paragraphs (short, standalone) | a document id | **one full news article** (`context`) |
| Does the context equal the gold evidence? | the gold paragraphs are the evidence; distractors are noise | no, it is the whole document | **no, it is the whole document**; the evidence is a few sentences inside it |
| Questions per unit | 1 question → its own paragraph set | many questions per document | **many questions per article** (test median 13) |
| Cross-document reasoning | yes (bridge paragraphs) | no | **no** |
| Standard corpus setup for RAG/KG | pool and deduplicate all paragraphs into one corpus | one index per document | **one index per document** (the paper puts the whole doc in the prompt) |
| Gold evidence labels | supporting-facts / paragraph labels | none | **partial**: recoverable from `@N` anchors for about 1/3 of questions |

## 5. What the released code does [verified from `src/`]

### 5.1 Inference (`src/llm/llm_inference.py`, `src/utils/prompt.py`)
- Reads `collected_test.json`, so **test is the evaluation split**.
- Prompt = one few-shot example + `"Document:\n" + full context` + an instruction + the question. The code that would truncate the document to 512 tokens is commented out, so the **full document is always sent**. T5 fine-tuning truncates at 1,024 tokens.
- Model: `gpt-3.5-turbo-1106`, temperature 0.2, max 100 output tokens.

### 5.2 Answer scoring (non-standard, and it matters for comparability)
```python
golden_answers = [a.split('@')[0].strip() for a in answer.split(',')]   # [] if answer is a list
for g in golden_answers:
    f1, p, r = hotpot_evaluate.f1_score(pred.lower(), g.lower())       # the WHOLE prediction vs EACH gold item
    append(f1, p, r)
final = mean over ALL (question, gold-item) pairs
```
What this means in practice:
- **Micro-averaged over gold items.** A question with 7 gold answers counts 7 times.
- **The full prediction string is scored against each gold item separately.** If a system correctly lists three victims, it gets recall 1.0 against each item but precision of about 1/3 against each. This is why the paper reports high recall and low precision, and why it prefers recall.
- **Unanswerable questions:** gold `[]` contributes **nothing** (it is skipped), while gold `""` always scores **0**.
- Normalization follows HotpotQA: lowercase, remove punctuation and articles.

To compare with the paper's numbers, reuse this exact scorer. Also report a per-question metric of your own, because the micro-average is hard to interpret.

### 5.3 What "Full Event KG" really is [inferred]
The structured-input variants (`golden-event`, `golden-trigger-arguments`, `golden-entity`, `golden-trigger`) are built from per-record fields `d['events']` and `d['relation']`. **Those fields are not in the released JSON.** In the generator (`sample.py`), each question stores `'events': [[event1], [event2]], 'relation': relation`, which are **the events of that question's own reasoning chain**. The prompt code also adds `(events[0].trigger, relation, events[1].trigger)` "for strategy 1".

So the "Full Event KG" gains in Table 4 most likely come from giving the model **the gold events and gold relation of the question's own chain, as an oracle**. The paper does not describe it as a KG extracted from the whole document. The paper's wording is ambiguous, and the data needed to confirm this is not released, so I cannot fully confirm it. Either way, **do not treat the paper's +KG numbers as the bar for an automatically built KG.** The honest comparison is against the paper's plain few-shot and CoT baselines, or better, your own full-document baseline using the same LLM.

### 5.4 Reproducibility gaps
The code reads `../data/meqa/...` and `../data/meqa/example.json` (the few-shot example), neither of which exists in the repo. It also needs the `events`, `relation` and `reasoning_chain` fields. **The released code cannot be run as-is.** Only the answer-only baselines can be reproduced from the released data.

## 6. How to use MEQA for KG evaluation

### 6.1 Recommended primary protocol: per-document KG, the faithful setup
1. **Split:** test (22 documents, 288 records). Drop the record with the empty question, and decide explicitly how to treat the 7 unanswerable ones (see step 5).
2. **Corpus unit:** one whitespace-normalized document. Group questions by normalized context, not by `example_id` prefix, because 4 ids have whitespace variants across splits.
3. **Build:** one KG per document, using only that document. Chunk inside the document as your system normally would. Test documents average about 590 tokens and the longest is about 1.2k, so one to a few chunks per document is typical.
4. **Answer:** query only the KG of that question's document. This matches the paper's `C + Q → A` setting, with the KG standing in for, or adding to, C.
5. **Score:**
   - **Comparable to the paper:** the exact MEQA scorer from §5.2, reporting P, R and F1 with recall as the headline. Note that it silently skips `[]`-answer questions.
   - **Interpretable:** a per-question metric, for example the max token-F1 over gold items, a set-level precision/recall over predicted vs. gold items, or an LLM-judge accuracy. Report the unanswerable questions separately.
   - **Optional retrieval metric:** for the 98 anchored test questions, map `@N` → WikiEvents trigger → `sent_idx` to get gold evidence sentences, then measure whether the KG retrieval surfaces them. This requires the WikiEvents files. The download URLs are in the Reproduction section below.
   - **Optional explanation metric:** the paper's completeness measure, applied to the KG's reasoning path. This only makes sense if your system outputs QA-style steps.
6. **Required baselines, same LLM and same prompts:**
   - (a) **full document in the prompt, no retrieval**: the paper's baseline and the realistic bar to beat;
   - (b) naive chunk RAG within the document;
   - (c) the KG method.

   Also report results by strategy (S1 / S2 / S35), since the paper does.
7. **More statistical power (optional):** the task is zero-shot for a KG pipeline, so you can also run on the **train** documents (188 docs, 1,629 questions), deduplicated by (context, question). **Do not** add dev: it is paraphrases of train questions on train documents. Keep test as the headline number for comparison with the paper.

This is structurally the same as the existing insurance-contract evaluation (one document with its own questions), so that harness is the natural template. Scale: test is about 13k tokens across 22 documents; all documents together are about 164k tokens.

### 6.2 Secondary protocol, only if you want a retrieval stress test: pooled corpus
You can pool the 22 test documents, or all 209, into one corpus and answer every question against a single KG, HotpotQA-style. **This is not how MEQA is defined**, and it has real problems:
- Most questions are only well-specified within their article ("Where were the explosions?"). With several articles about the same event in the pool (for example, 5 Boston Marathon articles in test), gold answers that belong to one article become ambiguous. A system can be scored wrong for giving an answer that is correct but comes from another article.
- Listing and counting questions ("How many events are related to injury?") are defined per document.

If you run it, label it as a non-standard variant, and do not compare the numbers with the paper or with the per-document setting.

### 6.3 What a KG may or may not buy you here (honest expectations)
- **Where a KG should help:** MEQA's difficulty is **event structure**: finding the right start event, following temporal or causal links, and gathering *all* arguments of a role (answers are often lists). The paper's error analysis names "incorrect start event" and "incorrect event relation" as the main failures **[paper App. L]**. An event-centric or n-ary/fact-style graph, where facts are anchored to triggers and roles, fits this better than plain entity–relation triples. The paper argues that argument-to-argument relations do not exist without going through the event.
- **Where it may not help:** retrieval is not the bottleneck. Documents are short, and the full-document baseline sees everything. A KG that loses information during extraction can **underperform** the full-document baseline. That is a legitimate result and should be reported as such.
- **Temporal and causal edges:** the gold relations were produced by GPT-3.5 and then curated, not annotated in the source corpus. Any temporal or causal edges your KG extracts are being compared against LLM-derived labels.
- **Noise ceiling:** about 15–22% of gold items are not verbatim spans, some answers are sentences, and a third of test questions contain template leftovers. Expect a ceiling well below 1.0. Human F1 is 0.811 **[paper Table 2]**.

## 7. Summary of cautions
1. The context is the **whole document**, not gold evidence. The task is **per document**. There is no cross-document reasoning.
2. **Dev is contaminated.** It contains train documents and paraphrased train questions. Use **test**.
3. `example_id` is **not unique**. Its prefix is the WikiEvents split, not the MEQA split.
4. Deduplicate documents on **whitespace-normalized** text. There are 209 unique texts behind 211 ids.
5. Question counts differ between the paper (2,243), the README (2,093) and the released files (2,099). Use the released files.
6. The paper's scorer is **micro over gold items, whole prediction vs. each item, and it skips `[]`**. Replicate it for comparability, and add a per-question metric.
7. The paper's **"Full Event KG" is very likely a per-question gold oracle**. It is not a bar for an extracted KG.
8. The released code cannot be run as-is, because the `events`, `relation` and example files are missing.
9. Counting questions count **WikiEvents trigger annotations**, and some answers are sentences or noise.
